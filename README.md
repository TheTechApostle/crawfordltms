# Crawford University — Lecture Timetable Management System

A full-stack Node.js/Express rebuild of the LTMS design document: course
proposal → Dean approval → session setup → course registration → best-fit
venue/timeslot allocation → sequential Lecturer → HOD → Dean → Registrar
approval → publication, with capacity-aware re-allocation on late
add/drops. Academic structure follows the real institutional hierarchy:
**Faculty → Department → Course**, with a Dean scoped to their faculty and
an HOD scoped to their department — each enforced server-side, not just
filtered in the UI. HODs propose and manage their department's courses,
Deans approve them, lecturers get assigned once approved, and only then can
students register. Lecturers can also set their own timetable slot
directly, constrained to whichever venues actually fit their class size.

## Stack

- **Backend:** Node.js, Express 5, `node:sqlite` (Node's built-in SQLite driver — file-based, zero setup, no native compilation required)
- **Views:** EJS (server-rendered), express-ejs-layouts
- **Frontend:** Bootstrap 5 + Font Awesome (Free), both self-hosted (copied into `public/vendor/` on `npm install` — no CDN dependency) — responsive sidebar/offcanvas nav, Bootstrap grid, cards, tables, forms, icon set throughout; a small `custom.css` retints Bootstrap's own CSS variables for the navy/gold Crawford identity and adds the weekly timetable grid
- **Auth:** express-session + bcrypt password hashing, role-based route guards

No build step, no external services — `npm install && npm run seed && npm start` is the whole setup. Requires **Node.js ≥ 22.5** (for `node:sqlite`).

## Getting started

```bash
cd crawford-ltms
npm install
cp .env.example .env
npm run seed     # creates db/crawford_ltms.sqlite with demo data
npm start         # http://localhost:3000
```

For auto-restart during development: `npm run dev` (uses Node's built-in `--watch`).

The Registrar seat is provisioned once, up front (same as any real
institution's IT setup) — it's not self-registerable. Everyone else
(**Lecturer, HOD, Dean, Student**) can also create their own account, each
on their own dedicated page — `/register/student`, `/register/lecturer`,
`/register/hod`, `/register/dean` — reachable directly from four separate
links on the sign-in page. There is no shared form, no combined "which
role are you" page, and no role dropdown anywhere: each link goes straight
to its own isolated page, and the role is fixed server-side per route — a
submitted form can't change what gets created, and a student can never end
up on the same page (or even the same form fields) as a Dean registration.

seat are deliberately left open in the seed data — try registering as
either to see the auto-seating behavior described below.

## A full walk-through

0. **Sign in as an HOD** (`hod.cs@…`) → *Courses* already has a pending
   proposal seeded (`CSC420 — Machine Learning`) alongside the department's
   approved courses. Propose a new one, or edit/delete the pending one — both
   are only available before a Dean has signed off. **Sign in as the dean**
   (`dean@…`) → *Course approvals* → **Approve** or **Reject** (with a
   reason). A rejected course goes back to the HOD, editable and
   resubmittable; approving unlocks **Offer this session** back on the HOD's
   *Courses* page, which creates the course offering the rest of this
   walk-through assumes already exists for the seeded courses.
1. **Sign in as the registrar** (`admin@…`) → *Sessions* is already seeded with
   an active `2025/2026 - First Semester`. *Faculties*, *Departments*, courses,
   venues and timeslots are pre-populated too.
2. Still as registrar, open **Allocation engine → Run allocation engine**.
   This pulls `registered_count` from enrollments, sorts course offerings
   largest-first, sorts venues largest-first, and assigns each course the
   *smallest* venue that still fits it, picking a timeslot that doesn't clash
   for that venue or lecturer. Anything that can't fit any venue is flagged
   as a **shortfall** on the dashboard. Open **Master timetable** for a
   bird's-eye grid of everything just allocated — time bands down the side,
   days across the top, click any course code for the full detail popup.
3. **Sign in as a lecturer** (`lecturer1@…`) → *My draft slots* → **Accept**
   (forwards to the HOD) or **Flag clash** (rejects with a reason — the
   engine immediately re-runs allocation for just that course and produces a
   fresh draft slot). Or skip the automatic engine entirely: *My courses*
   lets a lecturer view their roster and **set their own timetable slot**.
   The options list is computed server-side and only ever shows a timeslot
   paired with the smallest venue that actually fits the class — a course
   with 5 students registered will never be offered a 250-seat hall, even
   if that's the only venue technically free at some slot. Submitting sends
   it straight to the HOD queue, same as an accepted engine-generated slot.
4. **Sign in as the HOD** (`hod.cs@…`) → *Approval queue* → approve or reject
   (department-level clash check). This queue — and the approve/reject
   actions themselves — are scoped strictly to that HOD's own department;
   an HOD can't act on another department's entry even by guessing its id.
5. **Sign in as the dean** (`dean@…`) → *Departments* gives a faculty-wide
   view: every department under Faculty of Science with its HOD, course
   counts (approved/pending), lecturer and student counts, and how many
   courses are offered this session — plus a *Lecturers in charge* roster
   showing every offered course across the whole faculty, who's teaching
   it, how many are registered, and its current timetable status. Then
   *Approval queue* → final cross-department sign-off, scoped to the
   departments under this dean's own faculty — same protection as the HOD
   queue: a dean can't approve or reject an entry from another faculty even
   by guessing its id. *Cross-dept. clashes* lists any venue/timeslot pair
   double-booked across departments within that faculty.
6. **Back as the registrar** → *Publish queue* → **Publish**. This is the only
   action that makes an entry visible on read-only timetables.
7. **Sign in as a student** (`student1@…`) → *My timetable* now shows the
   published grid. **Course registration** lets a student register/drop
   courses for their level; dropping a course re-checks capacity and only
   triggers re-allocation if the drop pushes the class back under the
   currently assigned venue's capacity threshold — a published timetable is
   otherwise left untouched, per the design doc.

## Design notes

- **Allocation algorithm** (`services/allocationEngine.js`) implements the
  Best-Fit Decreasing rule from the document exactly: descending by
  registered count, descending venue capacity, smallest-fit match, fit-ratio
  computed for utilization reporting, shortfalls flagged for manual review.
- **Approval chain** (`services/approvalService.js`) enforces the sequential
  gate `draft → lecturer_ok → hod_ok → final → published`, and a reject at
  any stage re-runs the allocation engine for just that course offering
  (matching the sequence diagram in the design doc).
- **Late add/drop handling**: `handleLateChange()` only re-triggers
  allocation if the new registered count now exceeds the currently assigned
  venue's capacity — otherwise the published timetable is left untouched, to
  avoid unnecessary churn for students who already planned around it.
- Rejected timetable entries are kept (not deleted) as an audit trail in
  `approval_log`; only draft/shortfall attempts are cleared before
  re-allocating.
- **Faculty hierarchy**: `faculties` sits above `departments` (each
  department has a `faculty_id`), mirroring how Nigerian universities are
  actually structured. A Dean's functional scope comes from their own
  `users.faculty_id` — the same pattern already used for an HOD's
  `department_id`, a lecturer's `department_id`, or a student's
  `department_id`+`level`. `faculties.dean_id` and `departments.hod_id` are
  a separate, purely-cosmetic "who's the officially recognized head" pointer
  shown in the admin listings — they don't gate access on their own.
- **Scoped approvals, enforced server-side**: both `routes/hod.js` and
  `routes/dean.js` check that a timetable entry actually belongs to the
  approver's own department/faculty (`entryInDept` / `entryInFaculty`)
  *before* calling `approve()`/`reject()` — not just when building the
  approval-queue listing. An HOD or Dean can't act on someone else's
  entry by guessing or iterating ids; the request is silently dropped.
  The same guard pattern (`entryInDept` / `courseInFaculty`) protects course
  create/edit/delete/approve/reject too.
- **Course lifecycle**: `courses.status` is `pending` → `approved` (or
  `rejected`, which an HOD can edit and resubmit — back to `pending` with
  the reason cleared). An HOD can only create/edit/delete a course in their
  own department, and only while it's `pending`/`rejected` — once a Dean
  approves it, it's locked from further HOD edits (the registrar can still
  adjust it directly). Only an `approved` course can be offered for a
  session (`course_offerings`) — by the HOD from their own *Courses* page,
  or by the registrar from *Courses* — which is what makes it assignable to
  a lecturer and visible to students at their level. A course the registrar
  adds directly skips Dean review and goes straight to `approved` — the
  approval gate exists for HOD-originated proposals, not registrar ones.
- **Registrar edit/delete, everywhere it matters**: every academic-structure
  page the registrar manages — *Sessions*, *Faculties*, *Departments*,
  *Courses*, *Venues*, *Timeslots* — supports inline edit and delete, not
  just create. A delete is refused (button disabled, with a tooltip) if the
  row is still referenced elsewhere — a venue or timeslot already used in a
  timetable entry, a course already offered, a department with courses or
  members, a faculty with departments, a session with offerings — so this
  can't silently orphan live data. Reassigning a Faculty's Dean or a
  Department's HOD from these edit forms is a real change of authority, not
  just a label: the newly-picked person's own `faculty_id`/`department_id`
  is kept in sync, so their approval queue actually follows the reassignment.
  A Dean gets a narrower version of this: they can edit a still-`pending`
  course proposal in their own faculty (fixing a typo, say) before deciding
  on it, without having to reject-and-bounce it back to the HOD for
  something trivial — but, like the HOD, they lose edit rights once it's
  been decided either way.
- **Timetable grid, click for details**: *Master timetable* (registrar),
  *Department timetable* (HOD), and *Faculty timetable* (Dean) all render
  the same reusable grid (`views/partials/timetable-grid.ejs`) — time bands
  as rows, days as columns, so you can see at a glance how many classes are
  running in any slot. A cell with more than one class shows a count badge;
  every course code is a clickable chip that opens a shared modal
  (`views/partials/course-detail-modal.ejs`) with the full picture —
  department, lecturer, venue, capacity, registered count, and current
  approval status — populated client-side from the chip's own data
  attributes rather than a server round-trip. The Lecturer's and Student's
  personal timetables use the same modal on their existing day-column
  layout, so every entry anywhere in the app is click-for-details
  consistently. Each grid is scoped the same way its page already is —
  university-wide for the registrar, one department for the HOD, one
  faculty for the Dean — and only shows non-rejected entries that actually
  have a timeslot assigned. The grid's row structure comes from the
  registrar's configured *Timeslots*, not from existing entries — so the
  full grid (all time bands × all days) is visible from day one, with cells
  simply empty until the allocation engine runs or a lecturer self-schedules,
  rather than only appearing once something's been scheduled.
- **Lecturer self-scheduling** (`/lecturer/courses`): a lecturer can view
  their roster for any course they teach, and set their own timetable slot
  instead of waiting on the automatic engine.
  `getAvailableSlotsForOffering()` in `services/allocationEngine.js`
  computes, for the live registered count, every timeslot where the
  lecturer is free *and* a venue big enough for the class is free — pairing
  each with the **smallest** such venue. That option list is the only thing
  the lecturer can pick from: the server recomputes and re-validates the
  chosen timeslot on submit rather than trusting a posted venue id, so a
  class of 5 can never end up parked in a 250-seat hall just because that
  was technically free — the smaller room is always offered first, and
  nothing oversized is ever listed unless it's the only thing that fits. A
  self-scheduled entry lands at `lecturer_ok` (skipping the `draft` review
  step, since the lecturer is the one authoring it) and then follows the
  exact same HOD → Dean → Registrar chain as an engine-generated slot.
- **Self-registration** — the sign-in page links directly to four separate,
  dedicated forms: `/register/student`, `/register/lecturer`,
  `/register/hod`, `/register/dean` (`services/registration.js` holds the
  shared validation/creation logic). There's no intermediate page listing
  all four roles together — `/register` itself just redirects to `/login`,
  where the four links live side by side but each is its own link to its
  own page. Each route hardcodes its own role server-side rather than
  reading it from the submitted form, so there is no `role` field anyone
  could tamper with — which page you post to is the only thing that
  decides what account gets created. Each form only asks for what that
  role needs: department for lecturer/HOD, department+level for student,
  faculty for dean. If the department's HOD seat or faculty's Dean seat is
  currently open, the new account is auto-seated into it; if it's already
  filled, the account is still created with full role access — the
  registrar can reassign the official headship afterward via
  *Departments* / *Faculties*. The Registrar account itself is never
  self-registerable.

## Production notes

This ships with a dev-friendly setup: SQLite on disk and an in-memory
session store, which is fine for a single instance. For a real deployment:
set a strong `SESSION_SECRET` in `.env`, put a persistent session store in
front of `express-session` (e.g. `connect-sqlite3` or Redis) if you run more
than one process, and put the app behind HTTPS.
